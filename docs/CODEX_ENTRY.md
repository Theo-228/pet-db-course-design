# 官方 Codex 接手说明

## 接手顺序

1. 阅读仓库 `README.md`、`docs/PROJECT_CONTEXT.md`、`docs/DECISIONS.md`。
2. 阅读 `docs/chat-history/` 下的原始 ChatGPT 导出文件（如已上传），重点查找用户最终确认的范围与教师课程要求。
3. 先列出：已确认功能、尚未确认的问题、系统边界、拟用数据库核心实体和关键业务闭环。
4. 确认技术栈及约束后，再按需求分析 → 概念模型/ER → 逻辑模型/约束 → API → 前后端 → 测试与演示的顺序推进。

## 工作原则

- 严格区分原始聊天中的**用户要求**与**助手建议**，发生冲突时以最新用户明确决策为准。
- 所有 AI 能力只保留接口契约与占位实现，不连接实际模型服务。
- 不因使用场景不同而复制“家庭版/猫咖版”模块。
- 不未经讨论引入商业化、硬件端开发、微服务或不必要的大规模架构。
- 以 PostgreSQL 数据库课程设计质量为优先：表结构、主外键、约束、事务、查询、索引和完整业务流程。
- 先给出理解与设计路线，再大规模编写代码。
- 把重要决策持续更新在 `docs/DECISIONS.md`，保持 GitHub 可追踪。

## 原始对话的技术限制

从 ChatGPT 导出的 Markdown 是**历史快照**，不会随着 ChatGPT 的新消息自动更新到 GitHub。任何后续讨论都必须重新导出相关对话并提交更新，或将已经达成的新决策写入本仓库文档并提交。Codex 需要在开始新任务时主动重新读取必要文档。
