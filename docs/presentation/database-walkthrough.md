# PetOS 数据库零基础讲解

这份讲解面向第一次接触 PetOS 的汇报者。目标不是背下 17 张表，而是能解释：数据属于谁、如何产生、如何确定属于哪只宠物、数据库怎样防止错误，以及最终怎样形成统计或提醒。

## 先用一句话认识项目

PetOS 是宠物健康与智能设备工作台的课程原型。家庭和猫咖共用一套数据模型，每个使用单位对应一个 `workspace`。应用已有宠物、设备、测量、统计、阈值规则与提醒等闭环，但设备动作只是模拟，AI 接口只返回 501，尚无真实硬件或模型接入。功能边界见[项目 README](../../README.md)和[应用设计](../application-design.md)。

## 第一层：记住六张核心表

| 表 | 用容易理解的话说 | 为什么需要它 |
| --- | --- | --- |
| `workspace` | 一个家庭或一个使用单位的数据边界 | 把不同使用者的数据隔开 |
| `pet` | 宠物档案 | 记录相对稳定的身份资料，而非不断增长的测量历史 |
| `device` | 设备档案 | 记录设备种类、共享策略、所在区域和状态 |
| `device_pet_binding` | 设备与宠物在一段时间内的关联 | 设备可能换宠物使用，关联必须有有效期 |
| `measurement` | 一次原始观测 | 保存数值、指标、来源和采集时间，禁止改写或删除 |
| `measurement_attribution` | 对观测“属于哪只宠物”的判断 | 归属可以修正，但旧判断要可追溯 |

先会讲这六张表，就能解释数据库的主线。其他表分别补上账号权限、指标定义、自动化动作和查询结果。

## 第二层：跟着一条体重数据走

假设工作空间 A 里有猫“小橘”和一台专属体重秤。下面的数字仅用于讲解流程，不表示医学判断。

1. 创建宠物和设备时，两条记录都带 `workspace_id = A`。数据库中的组合外键阻止它们错误关联到其他工作空间的记录。
2. `device_pet_binding` 记录体重秤与小橘从何时开始绑定、何时结束。有效期采用左闭右开的 `[bound_at, unbound_at)`；如果设备是 `DEDICATED`，排他约束禁止它在同一时刻绑定两只宠物。
3. 体重秤上报 `weight_kg = 4.2`、采集时间和 `source_event_id`。`metric_type` 定义体重的单位与合理范围，`device_metric_capability` 确认体重秤有权上报体重。`measurement` 保存这条原始事实，同一设备的相同事件 ID 不能重复插入。
4. 如果测量时专属绑定有效，可以追加 `BINDING` 归属到小橘。若换成共享设备，仅有绑定不足以证明使用者身份，测量保持未知；取得身份证据后，才追加 `IDENTIFIED` 修订。原始测量不改。
5. `v_measurement_current` 把原始测量与最新归属合在一起读取；`v_pet_latest_weight` 从中找到宠物的最近体重。旧归属记录依然留在库中。
6. 写入测量时，触发器在同一事务中写入 `automation_dispatch`。后端在提交后处理规则；如果数值越过用户设置的阈值，可以产生提醒或模拟设备指令。这是确定性阈值规则，不是 AI 诊断。

一句话复述：**工作空间确定边界，绑定提供时间关系，测量保存事实，归属保存判断，视图提供当前读法，自动化处理后续动作。**

## 第三层：把其余表放回正确位置

| 模块 | 表 | 职责 |
| --- | --- | --- |
| 身份与组织 | `user_account`、`workspace_membership`、`space` | 账号、工作空间成员角色、区域 |
| 指标定义 | `metric_type`、`device_metric_capability` | 指标单位/范围/适用对象，设备种类可上报的指标 |
| 健康记录 | `health_record` | 人工记录观察、疫苗、治疗和就诊等事件 |
| 自动化 | `automation_rule`、`automation_dispatch`、`automation_execution` | 规则、持久化待处理任务、每次规则执行的历史 |
| 动作结果 | `alert_event`、`device_command` | 提醒和模拟设备指令，分别保存状态 |

上表连同前面的六张核心表共 17 张表。`database/migrations/V3__reporting_views.sql` 另定义四个普通视图，不是四张额外的表。

## 第四层：老师可能问的五种约束

| 机制 | 项目里的例子 | 防止什么错误 |
| --- | --- | --- |
| 组合外键 | `(workspace_id, pet_id)` 引用同一工作空间中的宠物 | A 空间数据串到 B 空间 |
| 排他约束 | GiST 检查设备绑定时间段是否相交 | 专属设备同一时刻属于两只宠物 |
| 唯一约束 | `(workspace_id, device_id, source_event_id)`；`(rule_id, measurement_id)` | 重复上报和重复规则执行 |
| `CHECK` 与触发器 | 指标范围、设备能力、活动时长、状态与动作一致性 | 形态合法但业务含义错误的数据 |
| 延期约束触发器 | 人工测量在同一事务内必须有 `MANUAL` 归属 | 事务提交后留下无法识别宠物的人工测量 |

数据库约束与后端校验不是重复劳动。后端负责身份、权限和友好的错误提示；数据库守住跨表关系与最终一致的业务不变量。数据库不会自己从 HTTP 请求中判断当前登录用户，后端必须核对 `workspace_membership`。

## 第五层：自动化为什么有三张表

- `automation_rule` 保存“什么指标满足什么阈值、触发什么动作”，当前仅支持单指标比较。
- `automation_dispatch` 是持久化待处理记录。它与原始测量在同一事务里写入，服务进程中断后仍可重新扫描。
- `automation_execution` 记录某条规则针对某条测量的一次执行，保存当时的规则快照和状态。唯一约束限制同一规则对同一测量重复执行。执行成功时，还要有匹配的 `alert_event` 或 `device_command`。

设备指令的 `APPLIED` 是课程版模拟状态，**不代表真实硬件已动作**。规则失败不会回滚原始测量；待处理行可以重试，但本版没有多节点分布式调度和历史规则版本回放。细节见[应用设计](../application-design.md)。

## 第六层：四个视图与查询性能

| 视图 | 回答的问题 |
| --- | --- |
| `v_measurement_current` | 一条原始测量当前归属于谁？ |
| `v_pet_latest_weight` | 每只宠物最近一次体重是多少？ |
| `v_pet_daily_totals` | 每天活动、进食、饮水各是多少？ |
| `v_device_last_measurement` | 每台设备最近上报了什么？ |

每日汇总按 `Asia/Shanghai` 日期计算。项目已为指标时间、设备时间、最新归属和待处理队列建立索引，但**不能仅凭“有索引”宣称性能已满足大规模生产负载**；应在真实数据量下用查询计划验证。当前测量表也没有提前分区。

## 常见答辩问答

**问：为什么不把体重直接写在 `pet` 表？**  `pet` 保存相对稳定的档案；体重会随时间产生多条记录。直接覆盖只剩最新值，历史趋势和采集来源都会丢失。原始观测因此进入 `measurement`。

**问：为什么测量和归属要拆成两张表？**  设备知道“测到了什么”，未必知道“是谁”。共享设备尤其如此。拆开后可保留原始事实，再追加可追溯的身份判断。

**问：只在前端筛选工作空间不行吗？**  不行。请求可以绕开前端直接发送。后端要校验成员权限，数据库组合外键要阻止跨工作空间错误关联；两者解决不同问题。

**问：为什么绑定用 `[开始, 结束)`？**  旧绑定在结束时刻失效，新绑定可以恰好在同一时刻开始，不会产生边界重叠。

**问：设备重复上报怎么办？**  设备事件 ID 与设备、工作空间一起受唯一约束保护。相同事件重复插入会被拒绝，避免重复测量和重复触发。

**问：后端处理测量后突然退出怎么办？**  待处理行已在写测量的事务中落库。重启后服务扫描未完成行；规则执行还有唯一约束减少重复动作风险。

**问：为什么现在不做测量表分区？**  课程规模尚无证据需要分区。提前分区会增加唯一约束、外键和维护复杂度。应先观察真实数据量与查询计划。

**问：目前是否具备真实 AI 诊断和设备控制？**  没有。AI 接口明确返回 501；设备指令只是模拟记录，真实硬件鉴权、回执和安全判断仍待实现。
