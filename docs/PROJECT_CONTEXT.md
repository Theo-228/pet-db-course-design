## 一、目标与范围（用户已确认）

1. 项目现阶段是**数据库课程设计**，要做前后端分离的完整数据库应用，而不只是一个 UI 原型或 AI 演示。
2. **统一宠物管理系统**：不要按“家庭用户 vs. 猫咖用户”分别设计业务模块或维护两套管理逻辑。尽量淡化人的角色和场景差异，以宠物数据、状态及业务事件为中心。这里的“淡化人的存在”不等同于彻底禁止必要的登录、审计或权限控制。
3. **暂不考虑商业化**，不要引入收费、订阅、营销等业务，除非用户后来明确要求。
4. **AI 不实现**：凡涉及 AI 健康分析、识别、预测、智能推荐等能力，只预留明确接口、数据契约和可替换的模拟返回（如确有必要），不接入实际 AI 模型，不把 AI 效果当作课程验收前提。
5. 项目需要使用 **Git 与 GitHub** 进行代码、文档和开发过程的同步/版本管理。
6. 重点应是**数据库设计合理、业务闭环完整、复杂度适中且可完成**。用户此前明确偏好“小而精”、数据库有实质性复杂度，但不要无限扩大规模。

## 三、目前建议的技术路线（建议，非已批准的硬性要求）

曾根据教师“前后端分离的数据库应用开发”课件讨论：

- 数据库：PostgreSQL（既有课程环境使用 PostgreSQL 17）。
- 后端：Java + Spring Boot + MyBatis，分层单体 REST API。
- 前端：Vue 3 + Vite + Element Plus + Axios。
- 代码管理：Git + GitHub，前端、后端、SQL、文档同仓库可行。

之前曾提议 Java 21、Spring Boot 3.5.x、PostgreSQL 17 等版本。**实施前要核对用户开发环境、课程要求和依赖兼容性**，不应盲目锁版本。教师是否强制某门语言或某个版本，以原始课件及用户确认信息为准。

## 四、面向数据库课程的实现侧重点（设计建议）

设计时应尽量让业务自然产生可展示的数据库机制，而不是为了炫技制造冗余：

- 明确实体、主外键、关联表、唯一性约束及合适的范式；
- 区分宠物基本档案、动态事件记录与可能的设备/健康数据，不让一张“大表”承载全部字段；
- 通过业务流程体现多表关联查询、历史状态追踪、必要的事务与一致性约束；
- 根据实际查询设计索引、视图、统计报表，必要时评估触发器/存储过程；
- 编写可复现的数据库初始化、示例数据、API 测试和课程演示流程。

上述均为**工程规划建议**，不是已经通过的具体功能需求。应先完成需求清单及 ER 设计，再讨论技术细节和实现顺序。
